## 작업 원칙

- Sprint 0은 신규 콘텐츠 추가보다 분석, 환경 재현성, 빌드 일관성, 기본 실행 안정성에 집중한다.
- 작업 하나를 완료할 때마다 구현 결과와 검증 근거를 같은 스프린트의 새 `Version_0.x.md`에 기록한다.
- 체크리스트가 하나라도 남으면 Sprint 1로 이동하지 않는다.
- Sprint 1 후보는 방향만 보존하며 Sprint 0 완료 조건에는 포함하지 않는다. Sprint 0 종료 시 우선순위를 다시 검토해 `Next_Version_Plan_1.md`의 정식 작업으로 승격한다.

## 필수 완료 항목

### 1. 빌드 환경 재현

- [x] **Visual Studio 2022 C++ 데스크톱 워크로드와 v143 MFC 구성요소를 설치한다.**
  - 이유: 현재 빌드가 `MSB8041`로 중단되어 실행 파일을 만들 수 없다.
  - 범위: 솔루션에 남길 아키텍처 모두에 대해 MFC/ATL 지원을 설치한다. Win32를 유지하지 않을 경우에는 구성 자체를 명시적으로 제거하고 이유를 기록한다.
- [x] **Windows SDK와 Platform Toolset 요구 버전을 문서에 고정한다.**
  - 이유: `WindowsTargetPlatformVersion=10.0`만으로는 새 PC에서 선택되는 SDK가 달라질 수 있다.
- [x] **C++ 언어 표준을 모든 Debug/Release 및 Win32/x64 구성에 동일하게 적용한다.**
  - 이유: 현재 C++20은 Debug x64에만 설정되어 있고 공통 소스는 `std::clamp`를 사용한다.
- [x] **Debug 콘솔 엔트리 포인트 설정을 정리한다.**
  - 이유: 현재 pragma가 Unicode MFC 엔트리 포인트와 충돌해 `LNK4258`로 무시된다. 콘솔이 필요하면 정식 디버그 설정이나 `AllocConsole` 경로를 사용하고, 필요 없으면 코드를 제거한다.
- [x] **정확한 빌드 명령과 필수 구성요소를 루트 README 또는 별도 빌드 문서에 기록한다.**
  - 이유: IDE에 의존하지 않고 새 개발 환경에서도 같은 결과를 재현해야 한다.

### 2. 저장소 기준선 정리

- [x] **`.gitignore`에 `.vs/`, `Debug/`, `x64/`, `*.aps`, `*.user`, TLOG/recipe 등 Visual Studio 생성물을 추가한다.**
  - 이유: 현재 개인 캐시와 과거 빌드 산출물이 다수 추적되어 변경 노이즈와 저장소 용량을 늘린다.
- [x] **이미 추적 중인 생성물을 Git 인덱스에서 제거하고 소스·리소스·문서만 남긴다.**
  - 이유: 깨끗한 체크아웃과 실제 빌드 결과를 구분할 수 있어야 한다.
- [x] **클린 빌드 전후 `git status`가 의도한 소스 변경 외에는 깨끗한지 확인한다.**
  - 이유: 빌드가 저장소 추적 파일을 매번 변경하면 재현 가능한 기준선을 유지할 수 없다.

### 3. 최소 실행 안정성 확보

- [x] **게임 루프를 이름 있는 단일 타이머로 통합하고 반환된 타이머 ID를 관리한다.**
  - 이유: ID 0과 1의 분리 타이머는 식별과 실행 순서를 신뢰하기 어렵다.
- [x] **경과 시간 또는 고정 시간 간격을 사용해 이동과 중력 계산을 갱신한다.**
  - 이유: 메시지 처리 지연이나 PC 성능에 따라 게임 속도가 달라지는 문제를 막는다.
- [x] **0 길이 드래그를 발사 취소로 처리한다.**
  - 이유: 방향 정규화 과정의 0 나눗셈과 NaN 전파를 차단한다.
- [x] **`Parent_ball::Init()`에서 속도, 힘, 클릭, 정지, 충돌 및 드래그 상태를 완전히 초기화한다.**
  - 이유: 재시작 이후 이전 프레임의 값이 다음 발사에 섞이지 않도록 한다.
- [x] **GDI 객체를 선택하기 전의 DC 객체를 저장하고 그리기 후 반드시 복원한다.**
  - 이유: 프레임마다 생성되는 비트맵·브러시·펜의 핸들 누수를 방지한다.
- [x] **메모리 DC 비트맵 선택도 RAII 또는 명시적 복원으로 안전하게 관리한다.**
  - 이유: 더블 버퍼용 비트맵이 DC에 선택된 채 파괴되는 문제를 막는다.
- [x] **`CChildView`의 포커스 메시지 맵을 연결하고 마우스 드래그에 Capture/ReleaseCapture를 적용한다.**
  - 이유: 창 밖 버튼 해제와 포커스 상실에도 입력·커서 상태가 정상 복구되어야 한다.
- [x] **페그 열 계산을 실제 80픽셀 간격과 화면 경계 기준으로 수정한다.**
  - 이유: 현재 88개 중 40개가 화면 오른쪽 밖에 생성된다.

### 4. 빌드 경고와 코드 기준선

- [x] **자체 코드의 `C4244` 형 변환 경고를 명시적이고 안전한 좌표 변환으로 제거한다.**
  - 이유: float 기반 게임 좌표와 정수 기반 GDI 좌표의 경계를 코드로 드러내야 정밀도 손실을 통제할 수 있다.
- [x] **경고 수준을 가능한 범위에서 `/W4`로 올리고 새 경고를 0개로 유지한다.**
  - 이유: 작은 프로토타입 단계에서 잠재 오류를 먼저 발견하는 비용이 가장 낮다.
- [x] **사용하지 않는 `ball_liner`와 미사용 필드의 유지·삭제 여부를 결정하고 기록한다.**
  - 이유: 실험 코드와 실제 실행 경로를 분명히 해야 이후 구조 개선이 안전하다.

## 검증 게이트

### 빌드 게이트

- [ ] 깨끗한 체크아웃에서 x64 Debug 빌드 성공 — 오류 0, 자체 코드 경고 0
- [ ] 깨끗한 체크아웃에서 x64 Release 빌드 성공 — 오류 0, 자체 코드 경고 0
- [ ] Win32 구성을 유지한다면 Win32 Debug/Release도 동일하게 성공
- [x] 빌드 결과 경로에 실제 `.exe`가 생성되고 필요한 MFC 런타임 정책이 문서화됨

### 실행 스모크 테스트

- [x] 프로그램이 시작되고 1000×800 게임 창, 툴바, 상태 표시줄이 정상 표시됨
- [x] 플레이어·적·배경·화면 안의 페그가 정상 표시됨
- [x] 일반 드래그 발사가 정상 동작함
- [ ] 클릭과 해제 위치가 같을 때 발사하지 않고 상태가 정상 유지됨
- [ ] 공이 좌·우 벽과 천장 경계에서 비정상 진동 없이 처리됨
- [ ] 페그 충돌 시 해당 페그가 한 번만 제거되고 피해량이 정확히 1 증가함
- [ ] 공이 화면 아래로 나가면 적 체력 또는 플레이어 체력과 턴 상태가 의도대로 변경됨
- [x] `Space`, `F5`, `새 게임`이 각각 일시정지, 공 초기화, 전체 초기화로 동작함
- [ ] 게임 클리어와 게임 오버 후 새 게임 상태로 정상 복귀함
- [ ] 창 밖 드래그, 포커스 전환, 창 종료 후 커서 제한이 남지 않음

### 안정성 게이트

- [ ] 10분 이상 반복 플레이 후 GDI 객체 수가 지속적으로 증가하지 않음
- [ ] 여러 번 재시작해도 공의 초기 위치·속도·입력 상태가 동일함
- [ ] Debug와 Release에서 발사 방향, 중력, 턴 결과가 체감상 동일함
- [ ] 실행과 종료 과정에서 ASSERT, 예외, 접근 위반이 없음

## Sprint 1 후보 백로그

다음 항목은 중요하지만 Sprint 0 완료 게이트에는 포함하지 않는다. Sprint 0이 끝난 뒤 `Next_Version_Plan_1.md`에서 범위와 수용 기준을 확정한다.

- 반발계수와 법선 반사를 사용한 Peglin형 페그 충돌 감각 개선
- 물리 상태, 전투 규칙, 렌더링을 `CChildView`에서 분리
- `float[2]`와 raw 포인터 getter를 2D 벡터 값 타입으로 교체
- 보드·벽·캐릭터 좌표를 하나의 설정/레이아웃 데이터로 통합
- 게임 상태 머신 도입: 조준, 발사, 낙하, 피해 정산, 승리, 패배
- 물리·턴 계산 단위 테스트 추가
- 점수, 피해 피드백, 애니메이션, 사운드 및 실제 Peglin형 콘텐츠 확장
